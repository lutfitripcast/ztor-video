Streaming stack proposal · Option 5B · September 2026

Stream a 4K film for cents, not hundreds of dollars.

Store and deliver every Ztor film on Cloudflare (R2 + CDN), lock paid rentals with DRM, and keep delivery cost close to zero. That leaves more of every rental for creators, co-creating fans and IP owners.

TL;DR

What we gain, what it costs, and what could go wrong.

  • Delivery is the big bill, and Cloudflare makes it $0. Every other provider charges for each GB sent to viewers. For one 4K film watched 1,000 times, that is $108 (Bunny) to $432 (AWS). With R2 + Cloudflare's CDN, it's a few cents in request fees.
  • About 90% cheaper per film than AWS or Google, and 70–90% cheaper than Bunny. The money we don't spend on delivery stays in the revenue pool.
  • DRM becomes our biggest cost, so we negotiate it. Every play needs a license. At $0.005 per license, one film costs about $10 a month in DRM. At the $0.02 list price, it's $40. We sign a volume contract before launch.
  • It is allowed. Cloudflare's terms let us serve video through its CDN as long as the files are hosted on R2 or Stream. No Enterprise contract needed to start.
  • The trade-off is build work. Bunny works in days. 5B takes weeks, because we connect encoding, packaging, DRM and players ourselves. Section 4 shows every step.

The services we use

One Cloudflare account covers most of it. Four outside pieces fill the gaps.

On Cloudflare

R2
Two buckets. ztor-masters (private: original uploads) and ztor-streams (encrypted video chunks, served through the CDN).
R2 event notifications
Says "a new file arrived" the moment a creator finishes uploading.
Queues
A waiting line for encoding jobs, so nothing gets lost when many uploads arrive at once.
Workflows
Runs each job step by step and retries a step if it fails.
Containers
Runs FFmpeg + Shaka Packager, the heavy video work. Sleeps (and costs nothing) when idle.
Workers
Small programs for upload links, payment checks, signed video links and the DRM key gate.
D1
A small database: film ID, encoding status, key IDs, who rented what.
CDN + custom domain + cache rules
Serves chunks from the nearest city (including Taipei and Phnom Penh). Chunks cached for a long time, playlists for a short time.
WAF / rate limiting
Blocks abuse of the key and link endpoints.
Stream (free content only)
For trailers and free clips. It can't do real DRM, and files it encodes must be served by Stream, so paid films never go through it.

Outside Cloudflare

DRM license service
EZDRM, BuyDRM, DoveRunner or Axinom. Issues Widevine, FairPlay and PlayReady keys. Pick by quote.
FFmpeg
Free encoder. Makes the 5 quality levels.
Shaka Packager
Free. Cuts video into chunks and encrypts them with keys from the DRM vendor.
Players
Shaka Player (web), AVPlayer (iPhone/iPad), Media3 (Android). All free.
Apple FairPlay deployment package
Apple must approve it before iPhones can play locked video. Start this first, since it takes time.
Rule of thumb: free video goes to Stream. Paid video goes to R2 + DRM. Never mix the two for the same file.

How to build it, step by step

Each step says what it does in plain words, then gives a prompt you can paste into Claude Code. Do them in order.

Creator uploads ─▶ R2 (masters) ─▶ event ─▶ Queue ─▶ Workflow
                                                        │
                                                        ▼
                                  Container: FFmpeg (5 sizes) + Shaka Packager (lock)
                                                        │   ▲ keys from DRM vendor
                                                        ▼
Fan pays popcorn ─▶ Worker (token) ─▶ Player ─▶ CDN ─▶ R2 (streams)
                                         │
                                         └─▶ Worker (key gate) ─▶ DRM vendor ─▶ key ─▶ video plays

  1. Open the accounts

    Like getting the keys to a building before moving in. Create the Cloudflare account on the $5 Workers Paid plan, pick a DRM vendor, and request Apple's FairPlay package today, because Apple takes the longest.

    Done when: you can log into Cloudflare and the DRM vendor dashboard, and the Apple request is sent.

  2. Make two storage boxes

    One private box for original films, one box for the locked chunks viewers stream. Connect the second box to a video subdomain (e.g. media.yourdomain.com) so the CDN serves it.

    Prompt for Claude Code
    Set up a Cloudflare Workers project with Wrangler for "ztor-video".
Create two R2 buckets:
1. ztor-masters — private, no public access.
2. ztor-streams — connected to a custom domain (placeholder: media.example.com).
Add both bucket bindings to wrangler.toml.
Add a cache rule plan: *.m4s / *.ts / *.mp4 cached 1 year (immutable), *.m3u8 / *.mpd cached 60 seconds.
Explain each command before running it. Don't make ztor-masters public.

    Done when: a test file in ztor-streams opens at the custom domain, and ztor-masters is not reachable from the internet.

  3. Let creators upload big files safely

    A Worker hands the creator a one-time upload link, so the huge file goes straight into storage without passing through our servers.

    Prompt for Claude Code
    Build a Worker endpoint POST /uploads that:
- requires a logged-in creator (stub the auth check with a TODO),
- creates a film record in D1 (table films: id, creator_id, title, status, created_at),
- starts an R2 multipart upload in ztor-masters at key masters/{filmId}/source.mp4,
- returns presigned part-upload URLs valid for 1 hour.
Add POST /uploads/{filmId}/complete to finish the multipart upload.
Include the D1 schema migration and a tiny test script that uploads a 200 MB file.

    Done when: a 2 GB test file lands in ztor-masters and its film record shows status "uploaded".

  4. Ring a bell when a film arrives

    When the upload finishes, storage automatically puts a "please encode me" ticket in a waiting line.

    Prompt for Claude Code
    Configure an R2 event notification on ztor-masters for object-create events with prefix "masters/".
Send events to a Cloudflare Queue named encode-jobs.
Write a queue consumer Worker that reads each message, finds the filmId from the key,
sets films.status = "queued" in D1, and starts a Cloudflare Workflow named encode-film with { filmId, key }.
Make it safe to receive the same event twice (idempotent).

    Done when: uploading a file changes its status to "queued" within a few seconds.

  5. Build the video machine

    A container holds two free tools. FFmpeg shrinks the film into 5 sizes so it plays smoothly on any internet speed. Shaka Packager chops it into small pieces and scrambles them.

    Prompt for Claude Code
    Create a Docker image for Cloudflare Containers (instance type standard-4) containing ffmpeg and shaka-packager.
Add a small HTTP server (Node, no extra deps) with POST /encode that receives:
  sourceUrl (presigned GET for the master), uploadBaseUrl info (presigned PUT URLs or a Worker upload endpoint), keys (from step 6).
The container has NO R2 binding — only use the presigned URLs it is given.
Steps:
1. ffmpeg: encode an H.264 ladder, 2-second GOP aligned across renditions:
   2160p ~16 Mbps, 1080p ~6 Mbps, 720p ~3 Mbps, 480p ~1.5 Mbps, 360p ~0.8 Mbps, plus AAC audio 128 kbps.
2. shaka-packager: output CMAF with HLS + DASH manifests, 6-second segments,
   encryption cbcs (works for FairPlay, Widevine and PlayReady), using the key IDs and keys passed in.
3. Upload every output to films/{filmId}/ in ztor-streams, then delete local temp files.
Log how many minutes each step took (we need this to check cost).

    Done when: a 10-minute test clip turns into playable (but locked) chunks in ztor-streams.

  6. Get the locks from the DRM vendor

    Before scrambling, we ask the DRM vendor for a new lock and key for this film. They keep the key safe; we only save the lock's ID.

    Prompt for Claude Code
    In the encode-film Workflow, add a step "get-keys":
- call our DRM vendor's CPIX / key API (vendor: [EZDRM | BuyDRM | DoveRunner | Axinom] — read their docs) to create
  one key for video and one for audio for filmId,
- request Widevine, PlayReady and FairPlay signaling data,
- store only key IDs (never the raw keys) in D1 table film_keys,
- pass keys to the container /encode call over HTTPS only, never log them.
Then add steps: "encode" (calls the container), "verify" (checks manifests exist), "publish" (status = "ready").
Retry each step up to 3 times with backoff.

    Done when: the film status reaches "ready" and D1 holds key IDs but no raw keys.

  7. Check the ticket before the movie

    When a fan pays with popcorn, a Worker gives them a short-lived pass. No pass means no playlist and no key.

    Prompt for Claude Code
    Build Worker endpoint POST /play/{filmId}:
- check the user is logged in and has an active rental for filmId (stub the popcorn/rental check behind a function hasRental(userId, filmId)),
- if yes, return a signed JWT (expires in 4 hours) with userId, filmId, deviceId,
  plus the manifest URLs (HLS + DASH) with a signed query token,
- if no, return 402 with message "Rent this film to watch it."
Add a Worker in front of media.example.com that rejects manifest requests without a valid token.
Segments can stay public-cached because they are encrypted.

    Done when: a user without a rental gets 402, and a user with one gets working playlist links.

  8. Guard the key door

    The player asks for the key. Our Worker checks the pass, then asks the DRM vendor to hand the key to that device only.

    Prompt for Claude Code
    Build Worker endpoint POST /license/{drm} where drm is widevine | fairplay | playready:
- require the JWT from /play,
- rate-limit to 10 requests per minute per user,
- forward the license request to the DRM vendor using their token/proxy method,
  with a policy: rental window 48 hours, no offline download for now, HDCP required for 2160p,
- log one row per license in D1 (userId, filmId, drm, time) so we can match the vendor's invoice,
- return the vendor response unchanged.

    Done when: the D1 license log count matches the vendor dashboard for a test day.

  9. Hook up the players

    Each device family uses its own lock system, so each app gets the player that speaks its language.

    Prompt for Claude Code
    Web: integrate Shaka Player. Use DASH + Widevine on Chrome/Android/Edge/Firefox and HLS + FairPlay on Safari.
Point license servers to /license/widevine and /license/fairplay, and send the JWT in a header.
iOS: AVPlayer with AVContentKeySession for FairPlay, fetching the certificate and license through our Worker.
Android: Media3 ExoPlayer with DefaultDrmSessionManager for Widevine, license URL = our Worker.
Show a clear message if the device can't play 4K: "This device plays up to 1080p."
Use the shared Ztor component library for all buttons and controls.

    Done when: the same rented film plays on Chrome, Safari, an iPhone and an Android phone.

  10. Add free content on Stream

    Trailers and free clips don't need locks, so they go on Cloudflare Stream, which encodes and plays them for us.

    Prompt for Claude Code
    Add a Cloudflare Stream upload path for free content only (trailers, Z-ORIGIN AI shorts, community clips).
Store stream_uid on the film or post record in D1. Use the Stream player for these.
Add a guard: any content marked paid must never be uploaded to Stream.

    Done when: a trailer plays via Stream, and uploading a paid film to Stream is blocked.

  11. Test before launch

    We measure real speed and real cost, because some numbers in this page are estimates.

    • Encode a real 1-hour 4K film, time it and compare the bill with the ~$1–2 estimate. If it's too slow, move encoding to a rented server.
    • Try to screen-record a locked film on each device. Protected devices should record a black screen.
    • Measure start time and buffering from Taipei, Hong Kong, Phnom Penh and an African city.
    • Check that the license count and cost match the DRM vendor invoice.

    Done when: all four checks pass, or each gap has a fix owner.

  12. Launch and watch the meters

    Go live with a small founding group of creators first, then open it up.

    • Weekly: DRM licenses per play (should stay near 2), cache hit rate (aim above 95%), encode minutes per film.
    • Alert if license requests spike, which can mean someone is abusing the key door.

Risks and how we handle them

Known unknowns, with the fix for each.

DRM price decides the win

At list price, DRM can cost more than Bunny's. Fix: get quotes from 4 vendors and sign a volume rate near $0.005 per license before launch.

4K is slow to encode

Cloudflare Containers top out at 4 vCPU, so a 4K film may take hours. Fix: time it in step 11; move to a rented server if needed.

4K needs the strongest lock

Studios usually require hardware-level DRM and HDCP for 4K. Weaker devices get 1080p. Fix: set the policy in step 8 and tell users clearly.

Apple approval takes time

No FairPlay means no locked playback on iPhone. Fix: request it on day 1.

Estimates, not quotes

Encode cost, Alibaba prices and some request counts are estimates. Fix: step 11 replaces them with real numbers.

We run more parts ourselves

More pieces than an all-in-one service. Fix: Eric's team owns the pipeline; the Revenue Engine only receives play and license events.
